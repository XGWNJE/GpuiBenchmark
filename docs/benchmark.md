# 测试协议

标准协议为 `gpui-benchmark-v1`，报告采用 schema 2。默认先确认实际生效的显示模式，再执行 10 个场景、各重复 3 轮。每场预热 3 秒、正式采样 20 秒，总计约 690 秒。

## 场景与负载

| 负载 | 数据行 | 模拟流 | 总更新量 / 秒 |
| --- | --- | --- | --- |
| 轻量 | 10,000 | 1 | 20 |
| 标准 | 50,000 | 4 | 400 |
| 高压 | 100,000 | 8 | 4,000 |
| 极限 | 200,000 | 16 | 16,000 |

四档分别测试热点更新与固定速度滚动，另测浅色、深色组件。热点集中到前 32 行，滚动按固定速度 240 dp/s 推进。被测列表或组件固定在可见区域，遥测图表可独立滚动。

一个独立线程模拟多路数据，生成带行号、增量与时间戳的更新批次，UI 线程消费。单批最多 128 条，队列最多 8 批，记录生成、消费、丢弃、未消费数量及批次排队延迟。数据采用固定种子，测试范围包含本机生成、队列、数值更新、虚拟列表和组件绘制。

测试期间请求当前分辨率下的最高刷新模式，确认实际模式后建立预算。结束后恢复窗口设置。失去前台、刷新模式或可用窗口改变时，报告标记为中断或无效。

## 统计与分数

每场正式采样保存完整的 CPU 侧帧回调间隔，计算平均、P95、P99、最大值和超预算次数。单场上限 100,000 个样本，溢出会标记无效。动态图表只显示近期 120 个回调，压力页原有手动统计保留最近 600 个回调。

每场计分项为以下三个值的乘积。

1. 全场回调次数除以采样时长。
2. `min(1, 帧预算 / P95间隔)`。
3. `min(1, 已应用更新 / 已生成更新)`。

综合分为 30 场计分项的平均值乘以 `1000 / 60`。服务端根据原始统计重新计算，每个厂商与机型组合保留最高标准成绩。刷新率、分辨率、温度和布局尺寸会影响分数，查看排名时结合报告中的设备与绘制上下文。

分数使用客户端上报的回调统计。GPU 呈现、触控到画面的延迟、持续温升和耗电通过系统侧工具另行测量。

## 一键系统采集

```powershell
pwsh -File scripts/benchmark-android.ps1
# 多设备时指定目标
pwsh -File scripts/benchmark-android.ps1 -Serial DEVICE_SERIAL
# 缩短的回归采样，生成报告
pwsh -File scripts/benchmark-android.ps1 -Quick
```

脚本自动安装匹配 ABI 的 Release 包，通过 Intent 启动场景序列，按本轮 run_id 获取报告。正式、快捷两种采样分别执行 30、10 个场景。快捷采样、模拟器、自定义参数和不完整测试均保留原因，标准机型榜接收完整标准协议。

系统证据包括 SurfaceFlinger 图层呈现统计、Perfetto、显示模式、前后内存和温度快照。SurfaceFlinger 使用全程前后计数差，覆盖启动与预热，结果保留毫秒桶精度。Perfetto 使用 128 MiB 环形缓冲区，长测试可能仅保留末段。Android 原生 Surface 的 FrameTimeline 覆盖情况由实际轨道验证，缺失时会明确记录。

输出复用 `.build/benchmark-results/latest`，预算 256 MiB，保留 App JSON、系统覆盖记录、原始 trace 和 HTML 汇总。工具按文件归属标记回收上轮输出，结束或失败时关闭自己创建的采集进程并收尾设备临时文件。

## 自动上传

标准测试结束后通过 HTTPS 上传机型、Android 版本、ABI、分辨率、刷新率、绘制上下文和各场统计。报告先原子写入应用目录，网络恢复、下次启动或下一次测试结束后自动补传。run_id 用于幂等提交。

排行榜入口为 [GPUI benchmark](https://visionguard.xgwnje.cn/gpui-benchmark/)。服务端校验报告结构、计数守恒和标准场景，保存明确的排名资格与原因。API 与部署位置见 [服务说明](../server/README.md)。
